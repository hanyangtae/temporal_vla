# 레포 검토·정리 설계 (2026-07-28)

exp2 이후 축적된 코드·문서를 파이프라인 축으로 순회하며 검토하고, 남길 것만 남긴다.

## 1. 목적

세 가지를 동시에 만족해야 한다.

1. **선별** — 다음 실험으로 넘어갈 때 유의미한 코드·문서만 남기고 중복 제거
2. **명명** — 사용자가 이해할 수 있는 이름 체계로 통일
3. **이해** — 정리 과정 자체가 사용자의 레포 이해 수단

3번이 설계를 지배한다. 에이전트가 자동으로 리팩터링하면 1·2는 달성되지만 3이 무너진다.
따라서 **역할은 지도 제작에 한정**하고, keep/archive 판정은 사용자가 코드를 직접 열어보고 내린다.

기간은 유동. 현재 추정 8~9일.

## 3. 순회 축과 순서

**파이프라인 축**(데이터 흐름)으로 순회한다. 같은 역할의 중복 구현이 한자리에 모여 보이고,
레포 구조 이해에 가장 직접적이기 때문이다.

```
S0 진입점 → D 문서 트랙 → S1 … S7 → S8 분석·시각화 → S9 운영 → 전역 rename
```

### 순서 근거

- **D를 S1 앞에 둔다.** 결과 문서를 먼저 읽어야 어떤 라운드가 종결됐고 무엇이 살아있는지가
  확정되고, 그것이 이후 모든 스테이지의 keep/archive 판정 근거가 된다.
- **S8을 뒤로 뺀다.** 17k로 단일 최대 덩어리지만 `vis/` 107개 파일 대부분이 라운드 1회용
  플롯일 가능성이 높다. 아카이브 후보 비율이 가장 높고 이해 가치는 가장 낮다. 앞 스테이지에서
  살아있는 라운드를 확정한 뒤라야 빠르게 쳐낼 수 있다.

## 5. 산출물

### 스테이지 카드 — `docs/review/S<N>_<이름>.md`

스테이지 진입 **직전에** 만든다(just-in-time). 미리 만들어두면 앞 스테이지의 적용 결과로 낡는다.

에이전트가 채우는 항목:

| 항목 | 근거 |
|---|---|
| 파일 표 (경로·LOC·최종수정일·역할 한 줄) | 코드 실제 독해 |
| 진입점 (실제 실행 명령, 라운드별로 다르면 전부) | `.sh` / 커밋 로그 / 문서 대조 |
| 의존 그래프 (import·호출 관계) | AST 파싱 |
| 중복 의심 쌍 | `dup_scan.py` 기계 탐지 |
| 도달 불가 파일 | 의존 그래프의 고아 노드 |
| 알려진 함정 | HANDOFF·agent-memory 대조 |

**판정 열은 빈칸으로 남긴다** (`keep` / `merge→<대상>` / `archive` / `미정`).
에이전트가 제안을 미리 적으면 사용자가 끄덕이고 넘어가게 되어 목적 3이 무너진다.
요청받을 때만 의견을 단다.

### 판정 원장 — `docs/review/LEDGER.tsv`

전 스테이지 통합 1개. 열: `파일 · 스테이지 · 판정 · 사유 · 적용여부 · 삭제커밋`.

주 역할은 **스테이지 간 판정을 실어 나르는 것**이다(S1 파일을 S6에 병합하는 등,
뒤 스테이지에 도달해야 실행 가능한 판정).

### 중복 탐지 도구 — `scripts/review/dup_scan.py`

"비슷해 보인다"가 아니라 수치 근거로 판정하기 위해. 100줄 안팎.

- 함수·클래스 단위 정규화 후 해시 → 완전 중복
- 파일 쌍 difflib 유사도 → 부분 복제 (라운드별 복사-수정 패턴)
- import 그래프 → 고아 파일

## 6. 적용 정책

**국소는 즉시, 전역은 마지막.**

| 판정 유형 | 적용 시점 | 이유 |
|---|---|---|
| 스테이지 내부 (고아 삭제, 아카이브, 내부 병합, 국소 rename) | 스테이지 끝에서 즉시 | 영향 범위가 닫혀 있고 그 자리에서 검증 가능 |
| 스테이지 간 (다른 스테이지 파일과 병합) | 원장에 기록 → 뒤 스테이지 도달 시 | 대상을 아직 안 읽었으므로 판정 불가 |
| 전역 명명 규칙 | 전 스테이지 완료 후 일괄 | 규칙은 전체를 본 뒤에야 정해진다. 이후 필요하면 개정 |

스테이지 종료 절차:

1. 판정을 원장에 기록
2. 국소 판정 적용 (mv / `git rm` / rename / 병합)
3. 진입점 재실행 — smoke 수준 "여전히 돌아가는가" 확인
4. 스테이지 단위 커밋

일괄 적용을 피하는 이유: 100여 건을 한꺼번에 적용하면 무엇이 무엇 때문에 깨졌는지 분리되지
않고, 며칠 전 판정의 맥락이 이미 소실된 상태에서 재검토하게 된다.

## 7. 아카이브 방식

**`git rm` + 원장에 직전 커밋 해시 기록.** `archive/` 디렉토리는 만들지 않는다 —
만들면 아무도 안 보는 쓰레기장이 되어 지금 정리하려는 상태를 이름만 바꿔 재생산한다.

복원: `git checkout <해시> -- <경로>`. 복원 명령을 원장에 그대로 적어둔다.

예외는 문서. 결과·판정 문서는 보존 대상이고, 종결된 계획·핸드오프는 기존 `docs/_legacy/`로 이동.
